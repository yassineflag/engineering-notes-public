# The Yocto Project for Embedded Linux

The Yocto Project builds a complete Linux system from source: the cross-toolchain, the bootloader, the kernel, every package, the root filesystem and the image written to the board. This note covers how its build tool (BitBake) and its metadata (layers, recipes, configuration) fit together, how to build a first image, and how to make the system your own with a layer that holds an image, a program, a kernel option and a distribution configuration. It ends with what a product needs: an SDK, reproducible builds, license and vulnerability reports, a read-only root and updates. The board is the BeagleBone Black used in the fundamentals notes.

Each piece that the fundamentals notes build by hand is built here by a recipe: the [toolchain](../../fundamentals/cross-compilation-toolchain/cross-compilation-toolchain_v2_2026-11-08.md), [U-Boot](../../fundamentals/bootloader/bootloader_v2_2026-11-09.md), the [kernel](../../fundamentals/kernel/kernel_v1_2026-11-10.md) and the [root filesystem](../../fundamentals/rootfs/rootfs_v1_2026-11-11.md). Section 13 of the rootfs note maps each hand-built piece to a Yocto variable; this note explains where those variables go.

**Assumptions:**
- The release is Yocto Project 6.0 "Wrynose", the long-term support (LTS) release of April 2026, supported until April 2030. Its headline versions are Linux 6.18, GCC 15.2 and glibc 2.43. Release 6.1 "Blacksail" (October 2026: Linux 7.2, GCC 16.2, glibc 2.44) is the current six-month release; section 21 lists what changes with it.
- The board is a BeagleBone Black (TI AM3358, one Cortex-A8, 512 MiB RAM, 4 GB eMMC, microSD slot), with the serial console on J1 at 115200 8N1, `ttyS0` in Linux.
- The machine configuration is `beaglebone-yocto`, from the reference BSP layer `meta-yocto-bsp`. The first build runs in QEMU (`qemux86-64`), which needs no hardware.
- The build machine is x86_64 Debian or Ubuntu, with at least 8 cores, 16 GiB of RAM and 100 GB of free disk space to be comfortable (section 3).
- Network addresses (board `192.168.0.50`) and device names (`/dev/sdX`) are placeholders, the same as in the other notes.

**Conventions:**
- `$` is a shell on the build machine, `#` a root shell on the board.
- **Expected** marks output reconstructed from the tools' messages, not captured. Versions, counts and sizes in it are placeholders.
- **From memory** marks file contents recalled from earlier releases and not re-read for this note. Check them in your copy of the layer.
- **Illustrative** marks a file that shows the shape of a solution and needs adapting.
- **Typical** marks sizes and durations given as orders of magnitude, not measured.

The commands follow the Yocto Project 6.0 documentation, read online in November 2026: the quick build, the manual setup, the fragments reference, the system requirements, and the migration guides from 5.1 to 6.1. - **The exact output of the tools.** Every output block is Expected.

The recipes and configuration files are written for this note and untested; read them before using them.

## 1. The mental model: metadata in, images out

Yocto is not a Linux distribution. It is a set of tools and build descriptions that produce one, made for your board and your product. Three things come together in a build:

```
 metadata (text files in layers)                        output
 ┌──────────────────────────────┐                ┌──────────────────────┐
 │ recipes (.bb)   what to build│                │ packages (rpm/ipk)   │
 │ classes         how to build │                │ root filesystem      │
 │ machine .conf   which board  │──> BitBake ──> │ kernel, DTB, U-Boot  │
 │ distro .conf    which policy │                │ card image (.wic)    │
 │ local.conf      this build   │                │ SDK installer        │
 └──────────────────────────────┘                │ license and SBOM data│
               ▲                                 └──────────────────────┘
               │ downloads source (tarballs, git) named in the recipes
```

- **BitBake** is the build tool: a task scheduler written in Python. It reads all the metadata, works out which tasks are needed (fetch, unpack, patch, configure, compile, install, package) for which recipes, and runs them in parallel in dependency order.
- **Metadata** says what to build. It lives in **layers**: directories of recipes and configuration, each one a git repository in practice.
- **The output** is everything the board needs, plus a record of what went into it.

**Nothing comes from the build machine.** Yocto builds its own cross-compiler and its own native tools (`make`, `python3`, `pkg-config`) before building anything for the target. That's why the first build takes hours, and also why the same metadata gives the same image on another machine.

**The names**, which are often used for each other:

| Name | What it is |
|---|---|
| Yocto Project | The umbrella project (Linux Foundation): releases, documentation, testing |
| BitBake | The build tool |
| OpenEmbedded-Core (OE-Core) | The base layer, `meta`: about a thousand recipes, the classes and the QEMU machines |
| meta-yocto | Two layers: `meta-poky` (the Poky distribution configuration) and `meta-yocto-bsp` (reference boards) |
| Poky | The reference distribution, `DISTRO = "poky"`. Also the name of a git repository that combined BitBake, OE-Core and meta-yocto: its `master` branch has not been updated since release 5.3, and `bitbake-setup` replaces it (section 4) |

**Yocto or Buildroot:**

| | Buildroot | Yocto |
|---|---|---|
| Configuration | One `.config`, Kconfig menus | Layers, recipes, variables in several files |
| Output | A root filesystem image; no packages | Packages, then images made from them |
| First build | Tens of minutes | One to several hours |
| Rebuild after a change | Often a full rebuild | Only what changed (shared state, section 18) |
| Several boards and products from one tree | Possible, by hand | What layers, machines and distros are for |
| Vendor support | Some | Most silicon vendors publish a Yocto BSP layer |
| Learning curve | Days | Weeks |

Buildroot fits one board and one firmware; Yocto fits a product family maintained for years. The [Buildroot note](../buildroot/) covers the other side.

## 2. The vocabulary

| Term | Meaning | File or variable |
|---|---|---|
| Recipe | How to fetch, build and package one piece of software | `busybox_1.37.0.bb` |
| Append file | Changes to a recipe, from another layer | `busybox_%.bbappend` |
| Class | Build logic shared by recipes (`autotools`, `cmake`, `kernel`, `image`) | `classes*/*.bbclass`, used with `inherit` |
| Layer | A directory of recipes, classes and configuration with a `conf/layer.conf` | `meta-bbb/` |
| BSP layer | A layer that describes hardware: machines, kernel, bootloader | `meta-yocto-bsp`, `meta-ti`, `meta-raspberrypi` |
| Machine | The board: CPU tuning, kernel, device trees, bootloader, console | `conf/machine/<name>.conf`, `MACHINE` |
| Distro | Policy for the whole system: C library, init system, features, versions | `conf/distro/<name>.conf`, `DISTRO` |
| Image | A recipe that lists the packages of a root filesystem and its formats | `core-image-minimal.bb` |
| Package | A piece of a recipe's output, installed into an image. One recipe gives several packages (`foo`, `foo-dev`, `foo-dbg`, `foo-doc`) | `PACKAGES`, `FILES:${PN}` |
| Package group | A recipe that only depends on a set of packages | `packagegroup-core-boot` |
| Task | One step of a recipe | `do_fetch`, `do_compile`, `do_install`... |
| Fragment | A named piece of build configuration, switched on with a command | `machine/qemux86-64`, `OE_FRAGMENTS` |
| Shared state (sstate) | Cache of task outputs, reused when the inputs are the same | `SSTATE_DIR` |
| SDK | A self-contained toolchain and sysroot for application developers | `bitbake -c populate_sdk` |

**Three questions, three files.** Most confusion goes away once a setting is put where it belongs:

| Question | Answered by | Example |
|---|---|---|
| Which hardware? | The machine | Cortex-A8, `zImage`, `am335x-boneblack.dtb`, `ttyS0` |
| Which kind of system? | The distro | glibc, systemd, no X11, package format |
| Which software in this root filesystem? | The image | BusyBox, Dropbear, your application |

`local.conf` answers a fourth one, "what's special about this build directory?": paths, parallelism, the choice of machine. Settings that define the product don't belong there, because `local.conf` isn't shared (section 11).
