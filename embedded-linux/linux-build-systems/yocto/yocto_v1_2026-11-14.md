# The Yocto Project for Embedded Linux

The Yocto Project builds a complete Linux system from source: the cross-toolchain, the bootloader, the kernel, every package, the root filesystem and the image written to the board. This note covers how its build tool (BitBake) and its metadata (layers, recipes, configuration) fit together, how to build a first image, and how to make the system your own with a layer that holds an image, a program, a kernel option and a distribution configuration. It ends with what a product needs: an SDK, reproducible builds, license and vulnerability reports, a read-only root and updates. The board is the BeagleBone Black used in the fundamentals notes.

Each piece that the fundamentals notes build by hand is built here by a recipe: the [toolchain](../../fundamentals/cross-compilation-toolchain/cross-compilation-toolchain_v2_2026-11-08.md), [U-Boot](../../fundamentals/bootloader/bootloader_v2_2026-11-09.md), the [kernel](../../fundamentals/kernel/kernel_v1_2026-11-10.md) and the [root filesystem](../../fundamentals/rootfs/rootfs_v1_2026-11-11.md). Section 13 of the rootfs note maps each hand-built piece to a Yocto variable; this note explains where those variables go.

**Assumptions:**
- The release is Yocto Project 6.0 "Wrynose", the long-term support (LTS) release of April 2026, supported until April 2030. Its headline versions are Linux 6.18, GCC 15.2 and glibc 2.43. Release 6.1 "Blacksail" (October 2026: Linux 7.2, GCC 16.2, glibc 2.44) is the current six-month release; section 21 lists what changes with it.
- The board is a BeagleBone Black (TI AM3358, one Cortex-A8, 512 MiB RAM, 4 GB eMMC, microSD slot), with the serial console on J1 at 115200 8N1, `ttyS0` in Linux.
- The machine configuration is `beaglebone-yocto`, from the reference BSP layer `meta-yocto-bsp`. The first build runs in QEMU (`qemux86-64`), which needs no hardware.
- The build machine is x86_64 Debian or Ubuntu, with at least 8 cores, 16 GiB of RAM and 100 GB of free disk space to be comfortable (section 3).
- Network addresses (board `192.168.0.50`) and device names (`/dev/sdX`) are placeholders, the same as in the other notes.

**Conventions:**
- `$` is a shell on the build machine, `#` a root shell on the board.
- **Expected** marks output reconstructed from the tools' messages, not captured. Versions, counts and sizes in it are placeholders.
- **From memory** marks file contents recalled from earlier releases and not re-read for this note. Check them in your copy of the layer.
- **Illustrative** marks a file that shows the shape of a solution and needs adapting.
- **Typical** marks sizes and durations given as orders of magnitude, not measured.

**Verification status:** nothing in this note was run. No source was downloaded, nothing was built, no image was booted. The commands follow the Yocto Project 6.0 documentation, read online in November 2026: the quick build, the manual setup, the fragments reference, the system requirements, and the migration guides from 5.1 to 6.1. Two points could not be confirmed:
- **The `beaglebone-yocto` machine in the 6.0 branch.** The machine has been in `meta-yocto-bsp` for many releases, but its file could not be read in the `wrynose` branch for this note. Section 9 shows how to check, and names the alternative (`beaglebone` from `meta-ti`).
- **The exact output of the tools.** Every output block is Expected.

The recipes and configuration files are written for this note and untested; read them before using them.

## 1. The mental model: metadata in, images out

Yocto is not a Linux distribution. It is a set of tools and build descriptions that produce one, made for your board and your product. Three things come together in a build:

```
 metadata (text files in layers)                        output
 ┌──────────────────────────────┐                ┌──────────────────────┐
 │ recipes (.bb)   what to build│                │ packages (rpm/ipk)   │
 │ classes         how to build │                │ root filesystem      │
 │ machine .conf   which board  │──> BitBake ──> │ kernel, DTB, U-Boot  │
 │ distro .conf    which policy │                │ card image (.wic)    │
 │ local.conf      this build   │                │ SDK installer        │
 └──────────────────────────────┘                │ license and SBOM data│
               ▲                                 └──────────────────────┘
               │ downloads source (tarballs, git) named in the recipes
```

- **BitBake** is the build tool: a task scheduler written in Python. It reads all the metadata, works out which tasks are needed (fetch, unpack, patch, configure, compile, install, package) for which recipes, and runs them in parallel in dependency order.
- **Metadata** says what to build. It lives in **layers**: directories of recipes and configuration, each one a git repository in practice.
- **The output** is everything the board needs, plus a record of what went into it.

**Nothing comes from the build machine.** Yocto builds its own cross-compiler and its own native tools (`make`, `python3`, `pkg-config`) before building anything for the target. That's why the first build takes hours, and also why the same metadata gives the same image on another machine.

**The names**, which are often used for each other:

| Name | What it is |
|---|---|
| Yocto Project | The umbrella project (Linux Foundation): releases, documentation, testing |
| BitBake | The build tool |
| OpenEmbedded-Core (OE-Core) | The base layer, `meta`: about a thousand recipes, the classes and the QEMU machines |
| meta-yocto | Two layers: `meta-poky` (the Poky distribution configuration) and `meta-yocto-bsp` (reference boards) |
| Poky | The reference distribution, `DISTRO = "poky"`. Also the name of a git repository that combined BitBake, OE-Core and meta-yocto: its `master` branch has not been updated since release 5.3, and `bitbake-setup` replaces it (section 4) |

**Yocto or Buildroot:**

| | Buildroot | Yocto |
|---|---|---|
| Configuration | One `.config`, Kconfig menus | Layers, recipes, variables in several files |
| Output | A root filesystem image; no packages | Packages, then images made from them |
| First build | Tens of minutes | One to several hours |
| Rebuild after a change | Often a full rebuild | Only what changed (shared state, section 18) |
| Several boards and products from one tree | Possible, by hand | What layers, machines and distros are for |
| Vendor support | Some | Most silicon vendors publish a Yocto BSP layer |
| Learning curve | Days | Weeks |

Buildroot fits one board and one firmware; Yocto fits a product family maintained for years. The [Buildroot note](../buildroot/) covers the other side.

## 2. The vocabulary

| Term | Meaning | File or variable |
|---|---|---|
| Recipe | How to fetch, build and package one piece of software | `busybox_1.37.0.bb` |
| Append file | Changes to a recipe, from another layer | `busybox_%.bbappend` |
| Class | Build logic shared by recipes (`autotools`, `cmake`, `kernel`, `image`) | `classes*/*.bbclass`, used with `inherit` |
| Layer | A directory of recipes, classes and configuration with a `conf/layer.conf` | `meta-bbb/` |
| BSP layer | A layer that describes hardware: machines, kernel, bootloader | `meta-yocto-bsp`, `meta-ti`, `meta-raspberrypi` |
| Machine | The board: CPU tuning, kernel, device trees, bootloader, console | `conf/machine/<name>.conf`, `MACHINE` |
| Distro | Policy for the whole system: C library, init system, features, versions | `conf/distro/<name>.conf`, `DISTRO` |
| Image | A recipe that lists the packages of a root filesystem and its formats | `core-image-minimal.bb` |
| Package | A piece of a recipe's output, installed into an image. One recipe gives several packages (`foo`, `foo-dev`, `foo-dbg`, `foo-doc`) | `PACKAGES`, `FILES:${PN}` |
| Package group | A recipe that only depends on a set of packages | `packagegroup-core-boot` |
| Task | One step of a recipe | `do_fetch`, `do_compile`, `do_install`... |
| Fragment | A named piece of build configuration, switched on with a command | `machine/qemux86-64`, `OE_FRAGMENTS` |
| Shared state (sstate) | Cache of task outputs, reused when the inputs are the same | `SSTATE_DIR` |
| SDK | A self-contained toolchain and sysroot for application developers | `bitbake -c populate_sdk` |

**Three questions, three files.** Most confusion goes away once a setting is put where it belongs:

| Question | Answered by | Example |
|---|---|---|
| Which hardware? | The machine | Cortex-A8, `zImage`, `am335x-boneblack.dtb`, `ttyS0` |
| Which kind of system? | The distro | glibc, systemd, no X11, package format |
| Which software in this root filesystem? | The image | BusyBox, Dropbear, your application |

`local.conf` answers a fourth one, "what's special about this build directory?": paths, parallelism, the choice of machine. Settings that define the product don't belong there, because `local.conf` isn't shared (section 11).

## 3. The build machine

**Supported distributions** for release 6.0 include Debian 11, 12 and 13, Ubuntu 22.04, 24.04 and 26.04, Fedora 42 and 43, openSUSE Leap 15.6 and 16.0, AlmaLinux and Rocky Linux 8 and 9. BitBake prints a warning on others. WSL 2 works but isn't tested by the project. Don't build on a Windows or macOS filesystem shared into a virtual machine: the build needs a case-sensitive Linux filesystem with hard links.

**Packages**, on Debian and Ubuntu (the list from the 6.0 quick build):

```sh
$ sudo apt-get install build-essential chrpath cpio debianutils diffstat file gawk gcc git \
      iputils-ping libacl1 libcrypt-dev locales python3 python3-git python3-jinja2 \
      python3-pexpect python3-pip python3-subunit socat texinfo unzip wget xz-utils zstd
$ locale --all-locales | grep en_US.utf8     # must print a line; else: sudo dpkg-reconfigure locales
```

The minimum versions are Git 1.8.3.1, tar 1.28, Python 3.9, GCC 10.1 and GNU make 4.0. On an older distribution, the project's "buildtools" tarball provides them (`bitbake-setup install-buildtools`).

**Resources:**

| Resource | Figure | Note |
|---|---|---|
| Disk | The documentation asks for 140 GB for `core-image-sato` (a graphical image). **Typical** for `core-image-minimal`: 40 to 60 GB | An SSD matters more than anything else |
| RAM | The documentation asks for 32 GB. **Typical**: about 2 GB per build thread; less works with lower parallelism (section 22) | Large C++ packages are what run out of memory |
| Time | **Typical**: 1 to 3 hours for a first minimal image on 8 cores; minutes afterwards | Downloads are a large share of the first build |
| Network | Several GB of source downloads on the first build | Then cached in `DL_DIR` |

**Never build as root.** BitBake refuses to run as root, and uses `pseudo` (a `fakeroot` equivalent, see the rootfs note, section 8) to give files root ownership in the image.

## 4. Getting the layers: bitbake-setup

Since release 5.3, the recommended way to get the layers is `bitbake-setup`, a tool shipped with BitBake. It reads a configuration that names the layer repositories and their revisions, clones them, and creates a build directory. The only thing cloned by hand is BitBake itself:

```sh
$ mkdir ~/yocto && cd ~/yocto
$ git clone https://git.openembedded.org/bitbake
$ ./bitbake/bin/bitbake-setup init
```

`init` asks five questions. For this note:

| Question | Answer | Meaning |
|---|---|---|
| Configuration | `poky-wrynose` | Release 6.0. `poky-master` is the development branch |
| BitBake configuration | `poky` | `poky-with-sstate` also downloads prebuilt task outputs from the project's servers (section 18) |
| Machine | `machine/qemux86-64` | For the first build; changed in section 9 |
| Distro | `distro/poky` | The reference distribution |
| Setup directory name | The default, or a short name | Default: `poky-wrynose-poky-distro_poky-machine_qemux86-64` |

The same without questions:

```sh
$ ./bitbake/bin/bitbake-setup init --non-interactive poky-wrynose poky distro/poky machine/qemux86-64
```

By default the setup directory is created under `bitbake-builds/` in the current directory. `bitbake-setup settings set --global default top-dir-prefix $HOME` moves it under your home directory for all later setups; `bitbake-setup settings list` shows the settings.

**What it creates.** The rest of this note calls the setup directory `$SETUP`:

```
$SETUP/
├── config/                  the configuration this setup was made from
├── layers/
│   ├── bitbake/             the build tool
│   ├── openembedded-core/   the meta layer: recipes, classes, QEMU machines
│   └── meta-yocto/          meta-poky and meta-yocto-bsp
└── build/
    ├── init-build-env       script to source in every new shell
    └── conf/
        ├── bblayers.conf    which layers this build uses
        ├── local.conf       settings of this build directory (nearly empty)
        ├── toolcfg.conf     written by bitbake-config-build: the enabled fragments
        └── auto.conf        written by bitbake-setup: SSTATE_DIR and others
```

**Other subcommands:**

| Command | What it does |
|---|---|
| `bitbake-setup list` | Lists the available configurations |
| `bitbake-setup status` | Shows how the setup differs from its configuration upstream |
| `bitbake-setup update` | Brings the layers to the revisions of the configuration |
| `bitbake-setup install-buildtools` | Installs the buildtools tarball into the setup |

**The manual way** still works, and shows what the tool does. The tags are named `yocto-<release>`:

```sh
$ mkdir -p ~/yocto/manual/layers && cd ~/yocto/manual
$ git clone -b yocto-6.0 https://git.openembedded.org/bitbake ./layers/bitbake
$ git clone -b yocto-6.0 https://git.openembedded.org/openembedded-core ./layers/openembedded-core
$ git clone -b yocto-6.0 https://git.yoctoproject.org/meta-yocto ./layers/meta-yocto
$ source ./layers/openembedded-core/oe-init-build-env
```

Use the tag of the latest point release (6.0.4 in November 2026) instead of `yocto-6.0` to get its security fixes. Tutorials written before 2026 start with `git clone git://git.yoctoproject.org/poky` and `source oe-init-build-env`: that still works for the older release branches (`scarthgap` and before), not for 6.0.

## 5. Building and running an image in QEMU

Every new shell needs the build environment. The script puts `bitbake` and the other tools in `PATH` and changes to the build directory:

```sh
$ source $SETUP/build/init-build-env
```

**The configuration of this build** is a list of fragments:

```sh
$ bitbake-config-build list-fragments
$ bitbake-config-build enable-fragment core/yocto/root-login-with-empty-password
```

- `machine/qemux86-64` sets `MACHINE`, and `distro/poky` sets `DISTRO`. Both were chosen by `init`.
- `core/yocto/root-login-with-empty-password` lets `root` log in without a password. It replaces the `debug-tweaks` image feature, removed in release 5.2. It's for development only (section 20).
- The command writes the list to `OE_FRAGMENTS` in `conf/toolcfg.conf`. Setting `MACHINE = "..."` in `conf/local.conf`, as older tutorials do, still works, but don't do both.

**Build:**

```sh
$ bitbake core-image-minimal
```

**Expected:**

```
Build Configuration:
BB_VERSION           = "<version>"
BUILD_SYS            = "x86_64-linux"
NATIVELSBSTRING      = "ubuntu-24.04"
TARGET_SYS           = "x86_64-poky-linux"
MACHINE              = "qemux86-64"
DISTRO               = "poky"
DISTRO_VERSION       = "6.0.4"
TUNE_FEATURES        = "m64 core2"
meta                 = "wrynose:<commit>"
meta-poky
meta-yocto-bsp       = "wrynose:<commit>"

Initialising tasks: 100% |##########################################| Time: 0:00:04
NOTE: Executing Tasks
...
NOTE: Tasks Summary: Attempted <N> tasks of which 0 didn't need to be rerun and all succeeded.
```

This header is the first thing to read in any build log, and the first thing to send when asking for help: it says which machine, which distro and which layer revisions were used.

**The images that come with OE-Core:**

| Image | Contents |
|---|---|
| `core-image-minimal` | Boots to a login: BusyBox, an init system, little else |
| `core-image-base` | Console image with full support for the machine's hardware |
| `core-image-full-cmdline` | Console image with the full GNU tools instead of BusyBox applets |
| `core-image-sato` | Graphical reference image |
| `core-image-minimal-initramfs` | A small initramfs |

**Run it in QEMU:**

```sh
$ runqemu snapshot nographic
```

`runqemu` finds the kernel and the root filesystem of the last image built for the machine. `snapshot` leaves the image file unchanged, and `nographic` puts the serial console in the terminal (leave with `Ctrl-A x`). Log in as `root`.

**The bitbake commands used most:**

| Command | What it does |
|---|---|
| `bitbake <recipe>` | Builds the recipe and everything it depends on |
| `bitbake -c <task> <recipe>` | Runs one task (`-c compile`, `-c menuconfig`, `-c devshell`) |
| `bitbake -c cleansstate <recipe>` | Removes the recipe's work directory and its shared state |
| `bitbake -f -c compile <recipe>` | Forces a task to run again |
| `bitbake -k <recipe>` | Keeps going after an error, as far as possible |
| `bitbake -e <recipe>` | Prints every variable and how it got its value (section 19) |
| `bitbake -g <recipe>` | Writes the dependency graph to `task-depends.dot` |
| `bitbake --runall=fetch <recipe>` | Downloads all the source without building |
| `bitbake -s` | Lists every recipe and its version |

## 6. The build directory: where everything goes

After a build, with the default settings:

```
build/
├── conf/                             section 4
├── downloads/                        DL_DIR: source tarballs and git clones
├── sstate-cache/                     SSTATE_DIR: shared state (bitbake-setup may place it
│                                     outside the build directory, see conf/auto.conf)
└── tmp/                              TMPDIR: everything that can be rebuilt
    ├── deploy/
    │   ├── images/<machine>/         kernel, DTBs, bootloader, root filesystem and card images
    │   ├── rpm/ (or ipk/, deb/)      the packages, a feed the board can install from
    │   ├── licenses/                 license texts and manifests per recipe and per image
    │   ├── spdx/                     SBOM data
    │   └── sdk/                      SDK installers
    ├── work/<arch>/<recipe>/<version>/    one work directory per recipe: WORKDIR
    ├── work-shared/                  source shared between recipes (kernel, gcc)
    ├── sysroots-components/          what each recipe offers to the others
    ├── log/                          cooker logs
    └── buildstats/                   time and resources per task
```

**The work directory of a recipe** is where to look when it fails:

| Path under `WORKDIR` | Contents | Variable |
|---|---|---|
| `sources/<name>-<version>/` | The unpacked and patched source | `S` (under `UNPACKDIR`) |
| `build/` | The build directory, for classes that build out of tree; otherwise `B` is `S` | `B` |
| `temp/` | `log.do_<task>` and `run.do_<task>` for every task | `T` |
| `recipe-sysroot/` | The target headers and libraries this recipe depends on | `STAGING_DIR_HOST` |
| `recipe-sysroot-native/` | The build-machine tools this recipe depends on | `STAGING_DIR_NATIVE` |
| `image/` | What `do_install` installed: the `DESTDIR` of the rootfs note | `D` |
| `packages-split/` | `image/` divided into packages | `PKGDEST` |
| `deploy-*/` | Package files before they are copied to `tmp/deploy` | |
| `rootfs/` | In an image recipe: the assembled root filesystem | `IMAGE_ROOTFS` |

`recipe-sysroot` is the "staging tree" of the rootfs note (section 14), made automatically, and separately for each recipe from its `DEPENDS`. A recipe can't see a library it didn't declare, which is how undeclared dependencies are caught.

**What to keep and what to delete:**

| Directory | Deleting it |
|---|---|
| `tmp/` | Safe. The next build restores everything from shared state in minutes |
| `sstate-cache/` | Safe, but the next build compiles everything again |
| `downloads/` | Safe, but everything is downloaded again. Worth sharing between build directories and backing up (section 20) |
| `conf/` | Your configuration. Keep it in version control, or better, reduce it to nearly nothing (section 11) |

To share downloads and shared state between build directories, in `conf/local.conf`:

```
DL_DIR = "${HOME}/yocto/downloads"
SSTATE_DIR = "${HOME}/yocto/sstate-cache"
```

## 7. Your own layer

Never edit the layers you downloaded: the changes are lost at the next update and nobody else has them. Everything of yours goes in your own layer, kept in your own git repository.

```sh
$ bitbake-layers create-layer ../layers/meta-bbb
$ bitbake-layers add-layer ../layers/meta-bbb
$ bitbake-layers show-layers
```

`create-layer` writes a skeleton, and `add-layer` adds its path to `BBLAYERS` in `conf/bblayers.conf`:

```
meta-bbb/
├── conf/layer.conf
├── COPYING.MIT
├── README
└── recipes-example/example/example.bb
```

`conf/layer.conf` is what makes a directory a layer (**Expected**):

```
# We have a conf and classes directory, add to BBPATH
BBPATH .= ":${LAYERDIR}"

# We have recipes-* directories, add to BBFILES
BBFILES += "${LAYERDIR}/recipes-*/*/*.bb \
            ${LAYERDIR}/recipes-*/*/*.bbappend"

BBFILE_COLLECTIONS += "meta-bbb"
BBFILE_PATTERN_meta-bbb = "^${LAYERDIR}/"
BBFILE_PRIORITY_meta-bbb = "6"

LAYERDEPENDS_meta-bbb = "core"
LAYERSERIES_COMPAT_meta-bbb = "wrynose"
```

| Variable | Meaning |
|---|---|
| `BBFILES` | Where recipes are looked for: `recipes-<group>/<name>/<name>_<version>.bb`. A recipe placed one directory too deep or too shallow is silently ignored |
| `BBFILE_PRIORITY` | When two layers have the same recipe and version, the higher priority wins. It also orders append files. It does **not** choose between versions: the highest version wins unless `PREFERRED_VERSION` says otherwise |
| `LAYERDEPENDS` | Layers this one needs. `core` is OE-Core |
| `LAYERSERIES_COMPAT` | The releases this layer was written for. BitBake refuses a layer that doesn't list the release in use |

**The layout this note fills in:**

```
meta-bbb/
├── conf/
│   ├── layer.conf
│   └── distro/bbb.conf                          section 11
├── recipes-apps/hello/
│   ├── hello_1.0.bb                             section 8
│   └── files/hello.c
├── recipes-core/
│   ├── images/bbb-image.bb                      section 10
│   └── busybox/
│       ├── busybox_%.bbappend                   section 12
│       └── files/bbb.cfg
└── recipes-kernel/linux/
    ├── linux-yocto_%.bbappend                   section 13
    └── files/bbb.cfg
```

**Finding existing layers.** Before writing a recipe, search the [OpenEmbedded Layer Index](https://layers.openembedded.org): it lists the public layers and their recipes per release. `meta-openembedded` (several layers: `meta-oe`, `meta-python`, `meta-networking`) holds most of what OE-Core doesn't. Take the branch named after your release (`-b wrynose`), and add the layers a layer depends on first.

## 8. Recipes: from source to packages

A recipe is a text file of variables and tasks. Here is a complete one for a C program, `recipes-apps/hello/hello_1.0.bb`:

```
SUMMARY = "Hello program for the BeagleBone Black"
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://${COMMON_LICENSE_DIR}/MIT;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = "file://hello.c"

S = "${UNPACKDIR}"

do_compile() {
    ${CC} ${CFLAGS} ${LDFLAGS} -o hello hello.c
}

do_install() {
    install -d ${D}${bindir}
    install -m 0755 hello ${D}${bindir}/hello
}
```

| Line | Meaning |
|---|---|
| File name | `<PN>_<PV>.bb`: the recipe name (`PN`) and version (`PV`) come from it |
| `LICENSE`, `LIC_FILES_CHKSUM` | Mandatory. The checksum of the license text makes the build fail if the license changes in a later version |
| `SRC_URI` | What to fetch. `file://` is looked up in `files/` next to the recipe; `https://` and `git://` are downloaded into `DL_DIR` |
| `S = "${UNPACKDIR}"` | Where the source is after unpacking. Needed when `SRC_URI` holds only local files. `S = "${WORKDIR}"`, found in older recipes, is an error since release 5.1 |
| `${CC} ${CFLAGS} ${LDFLAGS}` | The cross-compiler with the machine's tuning flags and the sysroot. Leaving `${LDFLAGS}` out fails a packaging check (section 22) |
| `${D}${bindir}` | `D` is the `DESTDIR`; `bindir` is `/usr/bin`. Always use the path variables (`bindir`, `sbindir`, `libdir`, `sysconfdir`, `datadir`), never literal paths |

```sh
$ bitbake hello
$ oe-pkgdata-util list-pkg-files hello
```

**The tasks of a recipe**, in order:

| Task | What it does |
|---|---|
| `do_fetch` | Downloads `SRC_URI` into `DL_DIR`, checks the checksums |
| `do_unpack` | Unpacks into `UNPACKDIR` |
| `do_patch` | Applies the `.patch` files of `SRC_URI` |
| `do_prepare_recipe_sysroot` | Fills `recipe-sysroot` from `DEPENDS` |
| `do_configure` | `./configure`, `cmake`, `meson setup`... |
| `do_compile` | `make`, `ninja`... |
| `do_install` | Installs into `D` |
| `do_package` | Divides `D` into packages, strips the binaries and puts the debug symbols in `-dbg` |
| `do_package_qa` | Checks the result (architecture, paths, missing dependencies) |
| `do_package_write_rpm` | Writes the package files |
| `do_populate_sysroot` | Offers headers and libraries to the recipes that depend on this one |

**Classes do the work for real projects.** A recipe for a project with a build system only names it:

```
SUMMARY = "Example library"
HOMEPAGE = "https://example.org/libfoo"
LICENSE = "BSD-3-Clause"
LIC_FILES_CHKSUM = "file://LICENSE;md5=<md5 of the file>"

SRC_URI = "git://example.org/libfoo.git;protocol=https;branch=main"
SRCREV = "<full commit hash>"

DEPENDS = "zlib openssl"

inherit cmake pkgconfig

EXTRA_OECMAKE = "-DBUILD_TESTS=OFF"
```

| Element | Meaning |
|---|---|
| `SRCREV` | The exact commit. With a tarball instead, `SRC_URI[sha256sum] = "..."` |
| `branch=` | Mandatory for `git://` since release 5.2 |
| No `S` line | The git fetcher unpacks where the default `S` expects it. `S = "${WORKDIR}/git"`, found in older recipes, must be removed since release 5.3 |
| `DEPENDS` | Build-time dependencies: recipes whose headers and libraries go in `recipe-sysroot` |
| `inherit cmake` | Provides `do_configure`, `do_compile` and `do_install`. Others: `autotools`, `meson`, `setuptools3`, `cargo`, `go`, `kernel`, `module` |
| `inherit pkgconfig` | Needed since release 6.0 by any recipe that calls `pkg-config` |
| `EXTRA_OECMAKE` | Options for the class: `EXTRA_OECONF` (autotools), `EXTRA_OEMESON`, `EXTRA_OEMAKE` |

**Build-time and run-time dependencies** are two variables:

| Variable | Names | When | Example |
|---|---|---|---|
| `DEPENDS` | Recipes | Needed to build this recipe | `DEPENDS = "zlib"` |
| `RDEPENDS:${PN}` | Packages | Installed in the image with this package | `RDEPENDS:${PN} = "bash"` |

Shared library dependencies are found automatically at packaging time, so `RDEPENDS` is only for what can't be seen in the binaries: scripts' interpreters, programs run by name, data files.

**Packages.** `do_package` divides what was installed. Each file goes to the first package whose `FILES` pattern matches:

| Package | Gets by default |
|---|---|
| `${PN}` | Programs, runtime libraries (`libfoo.so.1`), configuration |
| `${PN}-dev` | Headers, `libfoo.so` links, `.pc` files |
| `${PN}-dbg` | Debug symbols |
| `${PN}-doc`, `${PN}-locale-*` | Manual pages, translations |
| `${PN}-staticdev` | `.a` files |

A file installed outside the default patterns stops the build with `installed-vs-shipped`. Add it: `FILES:${PN} += "/opt/hello"`.

**Starting a service.** For systemd, install the unit file and name it:

```
inherit systemd
SYSTEMD_SERVICE:${PN} = "hello.service"

do_install:append() {
    install -D -m 0644 ${UNPACKDIR}/hello.service ${D}${systemd_system_unitdir}/hello.service
}
```

For SysV init, the equivalent is `inherit update-rc.d` with `INITSCRIPT_NAME` and `INITSCRIPT_PARAMS`. For a system user, `inherit useradd` with `USERADD_PACKAGES` and `USERADD_PARAM:${PN}`.

**Writing a recipe quickly:** `recipetool create -o hello_1.0.bb <URL or directory>` reads a source tree and writes a first version with the license, the dependencies and the class it could detect. `devtool add` does the same and sets up a workspace (section 16).

## 9. The machine: the BeagleBone Black

The machine configuration tells every recipe what hardware it builds for. Check that the reference one is in your copy of the layer, then switch to it:

```sh
$ ls ../layers/meta-yocto/meta-yocto-bsp/conf/machine/
$ bitbake-config-build enable-fragment machine/beaglebone-yocto
$ bitbake core-image-minimal
```

The second build reuses nothing compiled for x86: a different CPU means a different toolchain and different packages. Native tools are reused.

**What a machine file contains.** The essential lines of `beaglebone-yocto.conf` (**From memory** of earlier releases; read the file):

```
DEFAULTTUNE ?= "cortexa8hf-neon"
include conf/machine/include/arm/armv7a/tune-cortexa8.inc

PREFERRED_PROVIDER_virtual/kernel ?= "linux-yocto"
KERNEL_IMAGETYPE = "zImage"
KERNEL_DEVICETREE = "ti/omap/am335x-bone.dtb ti/omap/am335x-boneblack.dtb ti/omap/am335x-bonegreen.dtb"

SERIAL_CONSOLES ?= "115200;ttyS0 115200;ttyO0"

EXTRA_IMAGEDEPENDS += "virtual/bootloader"
UBOOT_MACHINE = "am335x_evm_defconfig"
SPL_BINARY = "MLO"
UBOOT_SUFFIX = "img"

IMAGE_FSTYPES += "tar.bz2 jffs2 wic wic.bmap"
WKS_FILE ?= "beaglebone-yocto.wks"
IMAGE_BOOT_FILES ?= "u-boot.${UBOOT_SUFFIX} ${SPL_BINARY} ${KERNEL_IMAGETYPE} ${KERNEL_DEVICETREE}"
MACHINE_EXTRA_RRECOMMENDS = "kernel-modules"
```

Every line is something done by hand in the fundamentals notes:

| Variable | By hand | Note |
|---|---|---|
| `DEFAULTTUNE` | `-mcpu=cortex-a8 -mfpu=neon -mfloat-abi=hard` | Toolchain note |
| `KERNEL_IMAGETYPE`, `KERNEL_DEVICETREE` | `make zImage dtbs` | Kernel note |
| `UBOOT_MACHINE`, `SPL_BINARY` | `make am335x_evm_defconfig`, `MLO` and `u-boot.img` | Bootloader note |
| `SERIAL_CONSOLES` | The `getty` line of `inittab` | Rootfs note, section 7 |
| `IMAGE_FSTYPES`, `WKS_FILE` | `mkfs.ext4 -d`, `genimage` | Rootfs note, sections 10 and 11 |
| `MACHINE_EXTRA_RRECOMMENDS` | `make modules_install` | Rootfs note, section 11 |

**The output**, in `tmp/deploy/images/beaglebone-yocto/` (**Expected**; most names are links to files with a timestamp):

| File | What it is |
|---|---|
| `MLO`, `u-boot.img` | The two stages of U-Boot |
| `zImage`, `am335x-boneblack.dtb` | Kernel and device tree |
| `modules-beaglebone-yocto.tgz` | Kernel modules |
| `core-image-minimal-beaglebone-yocto.rootfs.tar.bz2` | The root filesystem as an archive, for NFS root |
| `core-image-minimal-beaglebone-yocto.rootfs.wic` | The whole SD card: partition table, boot partition and root partition |
| `core-image-minimal-beaglebone-yocto.rootfs.wic.bmap` | Map of the blocks in use, for `bmaptool` |
| `core-image-minimal-beaglebone-yocto.rootfs.manifest` | The packages in the image and their versions |

**Writing the card.** Check the device name first (`lsblk`): the command erases it.

```sh
$ cd tmp/deploy/images/beaglebone-yocto
$ sudo bmaptool copy core-image-minimal-beaglebone-yocto.rootfs.wic /dev/sdX
```

`bmaptool` (package `bmap-tools`, or `bmaptool` on recent distributions) writes only the blocks in use and verifies them. Without it: `sudo dd if=<image>.wic of=/dev/sdX bs=4M conv=fsync status=progress`. Hold the S2 button while powering the board to boot from the SD card instead of the eMMC (bootloader note).

**Which BSP layer for a real product:**

| Layer | Machine for this board | Kernel | Use |
|---|---|---|---|
| `meta-yocto-bsp` | `beaglebone-yocto` | `linux-yocto`, close to mainline | Reference, learning, tested with every release |
| `meta-ti` (`meta-ti-bsp`), with `meta-arm` | `beaglebone` | TI's kernel and U-Boot, or mainline | Products on TI processors: all the SoC's peripherals supported |

For other boards, the silicon or board vendor's layer is the starting point: `meta-raspberrypi` (`raspberrypi4-64`), `meta-freescale` (NXP i.MX), `meta-st-stm32mp`, `meta-rockchip`. For your own board, write a machine file in your layer that starts from the closest existing one: `require conf/machine/<closest>.conf`, then change the device tree, the U-Boot configuration and the console.

## 10. Your own image

An image recipe lists what goes in the root filesystem. `recipes-core/images/bbb-image.bb`:

```
SUMMARY = "Console image for the BeagleBone Black"
LICENSE = "MIT"

inherit core-image

IMAGE_FEATURES += "ssh-server-dropbear"

IMAGE_INSTALL = "\
    packagegroup-core-boot \
    kernel-modules \
    hello \
    ${CORE_IMAGE_EXTRA_INSTALL} \
"

IMAGE_ROOTFS_EXTRA_SPACE = "65536"
```

```sh
$ bitbake bbb-image
```

| Variable | Meaning |
|---|---|
| `IMAGE_INSTALL` | Packages to install, with their dependencies. `packagegroup-core-boot` is the minimum to boot: BusyBox, the init system, the device manager, `base-files` |
| `IMAGE_FEATURES` | Named sets of packages and settings, see below |
| `IMAGE_FSTYPES` | Formats: `ext4`, `squashfs`, `tar.bz2`, `cpio.gz`, `ubifs`, `wic`. The machine sets defaults |
| `IMAGE_ROOTFS_EXTRA_SPACE` | Free space to add, in KiB |
| `IMAGE_LINGUAS` | Locales to install; `""` for none |
| `ROOTFS_POSTPROCESS_COMMAND` | Shell functions run on the assembled root filesystem. A last resort: a recipe is nearly always better |

**Image features** worth knowing:

| Feature | Effect |
|---|---|
| `ssh-server-dropbear`, `ssh-server-openssh` | An SSH server |
| `package-management` | Keeps the package manager and its database in the image |
| `read-only-rootfs` | Prepares the root filesystem to be mounted read-only (section 20) |
| `allow-empty-password`, `allow-root-login`, `empty-root-password`, `post-install-logging` | The four features that replaced `debug-tweaks`. Development only |
| `tools-debug` | `gdb`, `gdbserver`, `strace` |
| `dbg-pkgs`, `dev-pkgs` | The `-dbg` or `-dev` package of everything installed |
| `splash` | A boot splash screen |

**Adding a package for one build**, without touching the image recipe, in `conf/local.conf`:

```
IMAGE_INSTALL:append = " strace"
```

The leading space is required: `:append` doesn't add one. Use `:append`, not `+=`, in `local.conf`: `+=` there replaces the image's default list instead of extending it, because of the order in which the files are read (section 15).

**How the root filesystem is assembled.** `do_rootfs` installs the packages into an empty directory with the package manager, as a distribution installer would, and runs their post-install scripts. Scripts that can't run on the build machine are postponed to the first boot. Then `do_image_<type>` makes each format. Everything the rootfs note does by hand in sections 3 to 9 comes from packages: the directory skeleton and `fstab` from `base-files`, `passwd` and `group` from `base-passwd`, the startup scripts from `initscripts` or `systemd`.

## 11. Your own distribution configuration

The distro file holds the decisions that apply to every recipe. Poky is a reference to start from, not a product distribution. `conf/distro/bbb.conf` in your layer:

```
require conf/distro/poky.conf

DISTRO = "bbb"
DISTRO_NAME = "BBB Linux"
DISTRO_VERSION = "1.0"

INIT_MANAGER = "systemd"

DISTRO_FEATURES_OPTED_OUT += "x11 wayland opengl vulkan ptest"

PACKAGE_CLASSES = "package_ipk"
```

```sh
$ bitbake-config-build enable-fragment distro/bbb
```

Changing the distro rebuilds nearly everything: the features and the init system are inputs of most recipes.

| Variable | Meaning |
|---|---|
| `INIT_MANAGER` | `sysvinit`, `systemd`, `mdev-busybox` or `none`. Poky uses SysV init. Since 6.0, the two can't be combined, and the default without a distro (`nodistro`) became systemd |
| `DISTRO_FEATURES` | What the software is built with: `systemd`, `wifi`, `bluetooth`, `ipv6`, `x11`, `wayland`, `opengl`, `pam`, `usrmerge`, `seccomp`. Recipes switch options on and off from it |
| `DISTRO_FEATURES_OPTED_OUT` | Removes defaults. Since 6.0, `multiarch`, `opengl`, `ptest`, `vulkan` and `wayland` are added by default; this variable replaces `DISTRO_FEATURES_BACKFILL_CONSIDERED` |
| `TCLIBC` | `glibc` (default) or `musl` |
| `PACKAGE_CLASSES` | Package format: `package_rpm`, `package_ipk` (smallest tools on the board) or `package_deb` |
| `PREFERRED_VERSION_<recipe>` | Pins a version when several exist |
| `PREFERRED_PROVIDER_virtual/kernel` | Chooses between recipes that provide the same thing. Usually in the machine file |

**Features exist at three levels**, and recipes combine them:

| Level | Variable | Says | Example |
|---|---|---|---|
| Machine | `MACHINE_FEATURES` | What the hardware has | `usbhost`, `wifi`, `screen`, `rtc` |
| Distro | `DISTRO_FEATURES` | What the software supports | `wifi`, `systemd`, `bluetooth` |
| Image | `IMAGE_FEATURES` | What this root filesystem contains | `ssh-server-dropbear` |

Wi-Fi tools are installed by the base package group only when both the machine and the distro list `wifi`.

**`PACKAGECONFIG`** sets the options of one recipe. Each recipe lists its own:

```
PACKAGECONFIG:append:pn-curl = " mbedtls"
PACKAGECONFIG:remove:pn-curl = "openssl"
```

`:pn-curl` restricts the setting to the `curl` recipe, so it can live in the distro file. `bitbake -e curl | grep ^PACKAGECONFIG` shows the options and the current value.

**Keep `local.conf` nearly empty.** A product is defined by the machine, the distro and the image, all in version control. If a colleague needs your `local.conf` to get the same image, something is in the wrong file.

## 12. Changing existing recipes: bbappend files

An append file changes a recipe from another layer without editing it. It has the recipe's name with `.bbappend`, and `%` matches any version. `recipes-core/busybox/busybox_%.bbappend`:

```
FILESEXTRAPATHS:prepend := "${THISDIR}/files:"

SRC_URI += "file://bbb.cfg"
```

And `recipes-core/busybox/files/bbb.cfg`, a configuration fragment in the same form as the kernel's (kernel note, section 5):

```
CONFIG_TELNETD=n
CONFIG_FEATURE_VI_COLON=y
```

| Line | Meaning |
|---|---|
| `FILESEXTRAPATHS:prepend := "${THISDIR}/files:"` | Adds this layer's `files/` to the search path for `file://`. `:=` expands `THISDIR` now, while it still means the append file's own directory. The trailing `:` separates paths |
| `SRC_URI += "file://bbb.cfg"` | The BusyBox recipe merges every `.cfg` file of `SRC_URI` into its configuration |

**The common uses:**

| Goal | In the append file |
|---|---|
| Add a patch | `SRC_URI += "file://0001-fix.patch"`; `devtool` writes it for you (section 16) |
| Replace a configuration file the recipe ships | Put a file of the same name in your `files/`: yours is found first |
| Add a configure option | `EXTRA_OECONF += "--disable-foo"`, or `PACKAGECONFIG` |
| Install one more file | `do_install:append() { install -m 0644 ${UNPACKDIR}/extra.conf ${D}${sysconfdir}/ }` |
| Set something for one machine only | `SRC_URI:append:beaglebone-yocto = " file://bbb.cfg"` |

**Common targets on a small system:**

| Recipe | What an append changes |
|---|---|
| `base-files` | `fstab`, `motd`, the hostname: `hostname:pn-base-files = "bbb"` in the distro file |
| `busybox` | Applets, through `.cfg` fragments |
| `linux-yocto` | Kernel options and patches (section 13) |
| `u-boot` | Patches and the default environment |
| `systemd` | `PACKAGECONFIG`, default unit settings |

```sh
$ bitbake-layers show-appends | grep -A2 busybox
```

An append file whose recipe doesn't exist stops the parse (`No recipes in default available for ...bbappend`): it usually means a layer is missing or the version in the file name no longer exists. Use `%` rather than an exact version.

## 13. The kernel and the bootloader

**The kernel recipe** for the reference machines is `linux-yocto`: a kernel tree maintained by the project, close to the stable kernel (6.18 in release 6.0), configured from fragments instead of one defconfig. To change options, add a fragment in an append file, `recipes-kernel/linux/linux-yocto_%.bbappend`:

```
FILESEXTRAPATHS:prepend := "${THISDIR}/files:"

SRC_URI += "file://bbb.cfg"
```

Finding the options and writing the fragment:

```sh
$ bitbake -c menuconfig virtual/kernel        # opens the kernel's menuconfig in a terminal
$ bitbake -c diffconfig virtual/kernel        # writes the changes as a fragment, prints its path
$ bitbake -c kernel_configcheck -f virtual/kernel    # reports fragment options that were dropped
```

Copy the fragment that `diffconfig` wrote to `files/bbb.cfg`. Changes made with `menuconfig` alone are lost at the next clean build. `kernel_configcheck` is the same check as comparing the `.config` with the fragment by hand (kernel note, section 5): an option whose dependencies aren't met disappears silently.

**Kernel patches** go the same way: `SRC_URI += "file://0001-my-driver.patch"`, written with `devtool modify virtual/kernel` (section 16).

**A vendor or mainline kernel** has its own recipe. The shape of one that builds a git tree with an in-tree defconfig (**Illustrative**):

```
SUMMARY = "Mainline Linux for the BeagleBone Black"
LICENSE = "GPL-2.0-only"
LIC_FILES_CHKSUM = "file://COPYING;md5=<md5 of COPYING>"

inherit kernel

SRC_URI = "git://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git;protocol=https;branch=linux-6.18.y"
SRCREV = "<full commit hash>"
PV = "6.18+git"

KBUILD_DEFCONFIG = "omap2plus_defconfig"
COMPATIBLE_MACHINE = "beaglebone-yocto"
```

Select it in the machine or distro file with `PREFERRED_PROVIDER_virtual/kernel = "linux-mainline"`. The `kernel` class runs the steps of the kernel note: configure, `zImage`, `dtbs`, `modules`, and packages each module separately (`kernel-module-<name>`), with `kernel-modules` depending on all of them.

**Out-of-tree modules** use `inherit module`. The recipe needs a `Makefile` that follows the kernel's external-module conventions (kernel note, section 15), and the class supplies `KERNEL_SRC` and the cross-compilation variables. The package is named `kernel-module-<name>`; add it to the image, and list it in `KERNEL_MODULE_AUTOLOAD` to load it at boot.

**The bootloader** is the `u-boot` recipe, built for `UBOOT_MACHINE` and deployed next to the kernel. A product usually appends it with patches for its board and a default environment, or uses the vendor's recipe from the BSP layer. How the board finds the kernel (an `extlinux.conf`, a boot script or a FIT image) is decided by the machine file and the `.wks` file (section 14). Read `IMAGE_BOOT_FILES` and the machine's `UBOOT_*` variables with `bitbake-getvar` (section 19) rather than guessing.

**The device tree** for a custom board is a `.dts` added to the kernel as a patch, or built on its own with the `devicetree` class, then named in `KERNEL_DEVICETREE`.

## 14. The card image: wic

`wic` builds a partitioned image from the build's output, without root rights and without loop devices. It reads a kickstart file (`.wks`) named by `WKS_FILE`. The one for the reference machine (**From memory** of earlier releases):

```
part /boot --source bootimg_partition --ondisk mmcblk0 --fstype=vfat --label boot --active --align 4 --fixed-size 32 --sourceparams="loader=u-boot" --use-uuid
part / --source rootfs --ondisk mmcblk0 --fstype=ext4 --label root --align 4 --use-uuid
bootloader --append="console=ttyS0,115200"
```

| Element | Meaning |
|---|---|
| `part /boot --source bootimg_partition` | A FAT partition filled with the files of `IMAGE_BOOT_FILES`: `MLO`, `u-boot.img`, the kernel and the DTBs |
| `--active` | Sets the boot flag, which the AM335x ROM code requires to find `MLO` (bootloader note) |
| `part / --source rootfs` | The image's root filesystem |
| `--align 4` | Starts the partition on a 4 KiB boundary |
| `--use-uuid` | Refers to the partition by `PARTUUID` in `root=`, so the image boots whatever the device is called |
| `bootloader --append` | The kernel command line |

**A product layout** adds what the rootfs note describes in sections 15 and 16: two root partitions for A/B updates and a data partition (**Illustrative**):

```
part /boot --source bootimg_partition --fstype=vfat --label boot --active --align 4096 --fixed-size 64
part /     --source rootfs --fstype=ext4 --label rootA --align 4096 --fixed-size 512
part       --fstype=ext4 --label rootB --align 4096 --fixed-size 512
part /data --fstype=ext4 --label data --align 4096 --size 256
```

Put your file in `files/wic/` in your layer (required since 6.0; before, `wic/`) and set `WKS_FILE = "bbb-ab.wks"` in the machine or distro file.

```sh
$ wic list source-plugins                                  # what --source accepts
$ wic ls tmp/deploy/images/beaglebone-yocto/<image>.wic    # the partitions of an image
$ wic ls tmp/deploy/images/beaglebone-yocto/<image>.wic:1  # the files of partition 1
```

Since 6.0, `wic` is maintained in its own repository; plugin names use underscores (`bootimg_partition`, not `bootimg-partition`) since 5.3.

## 15. BitBake syntax: assignments and overrides

**Assignments:**

| Syntax | Meaning | When evaluated |
|---|---|---|
| `A = "x"` | Sets `A` | Variables inside are expanded when `A` is used |
| `A := "x"` | Sets `A`, expanding the value now | Immediately |
| `A ?= "x"` | Sets `A` if it has no value yet | At parse time, in file order |
| `A ??= "x"` | Sets a weak default: used only if nothing else sets `A` | At the end of parsing |
| `A += "x"`, `A =+ "x"` | Appends or prepends with a space | Immediately |
| `A .= "x"`, `A =. "x"` | Appends or prepends without a space | Immediately |
| `A:append = " x"`, `A:prepend = "x "` | Appends or prepends without a space | After everything else |
| `A:remove = "x"` | Removes the word `x` | Last of all; can't be undone by another file |

**`+=` and `:append` aren't the same.** `+=` acts when the line is read, so a later `A = "..."` or an earlier `A ?= "..."` cancels or changes it. `:append` is applied at the end, whatever the order. In a recipe or an append file, `+=` is fine. In `local.conf` and distro files, which are read before the recipes, use `:append`.

**Overrides** make a value conditional. A suffix after `:` applies when it's in the `OVERRIDES` list:

```
SRC_URI:append:beaglebone-yocto = " file://bbb.cfg"     # this machine only
EXTRA_OECONF:append:arm = " --disable-asm"              # every 32-bit Arm machine
CFLAGS:append:pn-hello = " -DDEBUG"                     # this recipe only, from a .conf file
RDEPENDS:${PN}:append:libc-musl = " musl-utils"         # with musl only
```

The list holds the machine name, the architecture, the distro name, `pn-<recipe>`, `libc-glibc` or `libc-musl`, `class-target`, `class-native`. Until release 3.4 (2021) the separator was `_` (`SRC_URI_append`): tutorials and layers that use it don't parse anymore.

**Files are read in this order:** `bblayers.conf`, each `layer.conf`, then `bitbake.conf`, which includes `auto.conf`, `local.conf`, the distro file, the machine file and the default settings; then the classes; then each recipe followed by its append files in layer priority order.

**Functions:**

```
do_install:append() {
    install -d ${D}${sysconfdir}/hello          # shell, added to the end of do_install
}

python do_show_machine() {
    bb.plain("machine: %s" % d.getVar("MACHINE"))    # Python, with the datastore d
}
addtask show_machine after do_configure before do_compile

SRC_URI += "${@bb.utils.contains('DISTRO_FEATURES', 'systemd', 'file://hello.service', '', d)}"
```

`${@...}` is inline Python; `bb.utils.contains(variable, word, if_true, if_false, d)` is the most used helper.

## 16. devtool: working on source code

`devtool` manages a workspace layer where a recipe's source is an ordinary git tree. The build uses that tree instead of the downloaded source.

**Changing an existing recipe:**

```sh
$ devtool modify busybox                       # source in build/workspace/sources/busybox, as a git tree
$ cd workspace/sources/busybox                 # edit, then git commit
$ devtool build busybox
$ devtool deploy-target busybox root@192.168.0.50     # copies the built files to the running board
$ devtool finish busybox ../layers/meta-bbb    # writes your commits as patches and a .bbappend, closes the workspace
```

| Command | What it does |
|---|---|
| `devtool add <name> <URL or path>` | Creates a recipe for new software and puts it in the workspace |
| `devtool modify <recipe>` | Extracts the source of an existing recipe, patches applied as commits |
| `devtool build <recipe>` | Builds from the workspace source |
| `devtool deploy-target`, `undeploy-target` | Copies the result to a board over SSH, and removes it again |
| `devtool build-image <image>` | Builds an image that includes the workspace recipes |
| `devtool upgrade <recipe> -V <version>` | Moves a recipe to a new upstream version and rebases its patches |
| `devtool finish <recipe> <layer>` | Moves the recipe or the append file and the patches into a layer |
| `devtool status`, `devtool reset <recipe>` | Lists the workspace; drops a recipe from it |

`deploy-target` needs an SSH server on the board (`ssh-server-dropbear`). It isn't a package installation: it's for the edit, build and test loop. A recipe still in the workspace makes every build print a warning, and a forgotten one is a common cause of "my change in the layer has no effect".

## 17. The SDK: building applications outside Yocto

Application developers don't need BitBake. The SDK is an installer with the cross-toolchain, the target's sysroot matching an image, and an environment script:

```sh
$ bitbake -c populate_sdk bbb-image
$ ls tmp/deploy/sdk/
$ sh tmp/deploy/sdk/<distro>-glibc-x86_64-bbb-image-cortexa8hf-neon-beaglebone-yocto-toolchain-<version>.sh
```

It asks for an installation directory (default under `/opt/<distro>/<version>`). Then, in every shell that builds for the board:

```sh
$ . /opt/<distro>/<version>/environment-setup-cortexa8hf-neon-poky-linux-gnueabi
$ echo $CC
$ $CC -O2 -o hello hello.c
```

**Expected:**

```
arm-poky-linux-gnueabi-gcc -mthumb -mfpu=neon -mfloat-abi=hard -mcpu=cortex-a8 ... --sysroot=/opt/<distro>/<version>/sysroots/cortexa8hf-neon-poky-linux-gnueabi
```

The script sets `CC`, `CXX`, `LD`, `CFLAGS`, `LDFLAGS`, `PKG_CONFIG_SYSROOT_DIR`, `PKG_CONFIG_PATH` and `CONFIGURE_FLAGS`, and provides a CMake toolchain file (`OE_CMAKE_TOOLCHAIN_FILE`) and a Meson cross file. It's the settings file of the toolchain note, generated. Use `$CC`, not the bare compiler name: the tuning flags and the sysroot are in the variable.

| | Standard SDK | Extensible SDK |
|---|---|---|
| Built with | `bitbake -c populate_sdk <image>` | `bitbake -c populate_sdk_ext <image>` |
| Contains | Toolchain, sysroot | The same, plus `devtool` and the shared state to build recipes |
| Size | **Typical**: hundreds of MiB | Several GiB |
| For | Building an application with its own build system | Developers who also write recipes |

The sysroot contains the `-dev` packages of what the image installs. A library that's missing from the SDK is missing from the image: add it to the image (or to `TOOLCHAIN_TARGET_TASK`) and rebuild the SDK. Rebuild and redistribute the SDK whenever the image's libraries change.

## 18. Shared state: why rebuilds are fast

For every task, BitBake computes a **signature**: a hash of the task's code, the variables it uses, and the signatures of the tasks it depends on. The output of the main tasks (`populate_sysroot`, `package`, `package_write_*`, `deploy`, `populate_lic`) is stored in the shared state cache under that signature. When a build needs a task whose signature is already in the cache, it takes the stored output and skips the fetch, configure and compile tasks before it.

What follows from it:

- **A change rebuilds what depends on it.** Editing a recipe rebuilds that recipe and, by default, the recipes that link against it. Changing a distro feature or the C library rebuilds nearly everything.
- **`tmp/` can be deleted.** The next build restores it from the cache.
- **`cleansstate` is rarely needed.** If a change isn't picked up, the cause is almost always that the change isn't where BitBake reads it (section 19), not a stale cache.
- **The cache can be shared**: between build directories (`SSTATE_DIR`), and between machines over HTTP (`SSTATE_MIRRORS`). A team's CI server usually publishes its cache so that developers compile only what they changed.
- **Hash equivalence** goes one step further: when a rebuilt recipe gives the same output as before, the recipes that depend on it aren't rebuilt. It's on by default (`BB_SIGNATURE_HANDLER = "OEEquivHash"`, `BB_HASHSERVE = "auto"`).

The project publishes its own cache. `bitbake-config-build enable-fragment core/yocto/sstate-mirror-cdn` (or the `poky-with-sstate` configuration of section 4) makes a first build of the reference images mostly a download.

**Finding out why something was rebuilt:**

```sh
$ bitbake -S printdiff bbb-image             # compares signatures with the closest ones in the cache
$ bitbake-diffsigs -t busybox do_configure   # the difference between the last two signatures of a task
```

## 19. When a build fails

**Read the right log.** The console shows the end of the failing task's log and its path:

```
ERROR: hello-1.0-r0 do_compile: oe_runmake failed
ERROR: Logfile of failure stored in: .../tmp/work/cortexa8hf-neon-poky-linux-gnueabi/hello/1.0/temp/log.do_compile.12345
```

Next to it, `run.do_compile` is the exact shell script that was run. Scroll up to the first error: with parallel `make`, the last lines are often about another file.

**Where does this value come from?** The most useful command in Yocto:

```sh
$ bitbake-getvar -r busybox SRC_URI
$ bitbake -e busybox | less               # every variable; search for ^SRC_URI=
```

Both print the final value and, before it, every file and line that set, appended to or removed from the variable. This answers "why isn't my setting applied?": either the line isn't read (the layer isn't in `bblayers.conf`, the file name doesn't match), or a later line wins. Without `-r`, `bitbake-getvar` shows the global configuration (`bitbake-getvar MACHINE`).

**Is my file read at all?**

```sh
$ bitbake-layers show-layers                 # the layers and their priorities
$ bitbake-layers show-appends                # which append files apply to which recipes
$ bitbake-layers show-recipes "busybox*"     # which layer provides which version
$ bitbake-layers show-overlayed              # recipes hidden by a higher-priority layer
```

**Working inside a recipe's build:**

```sh
$ bitbake -c devshell hello        # a shell in S with the cross-compilation environment set
$ bitbake -c compile -f hello      # run one task again
$ bitbake -c listtasks hello       # the tasks of a recipe
```

In the devshell, `$CC`, `make` and `./configure` behave as in the task, which makes it the place to try a fix before writing it in the recipe.

**What's in the image, and why?**

```sh
$ oe-pkgdata-util find-path /usr/bin/hello        # which package ships a file
$ oe-pkgdata-util list-pkg-files busybox          # the files of a package
$ oe-pkgdata-util lookup-recipe libcrypto3        # which recipe makes a package
$ bitbake -g bbb-image && grep hello pn-buildlist # the recipes an image builds
```

The image's `.manifest` file lists the installed packages. To track how an image changes from build to build (packages, sizes, files), enable build history with `INHERIT += "buildhistory"`: it writes a git repository in `buildhistory/`, and `buildhistory-diff` compares two builds.

**Packaging checks (QA).** `do_package_qa` stops the build on these:

| Message | Meaning | Fix |
|---|---|---|
| `installed-vs-shipped` | Files installed but in no package | `FILES:${PN} += "..."`, or remove them in `do_install:append` |
| `already-stripped` | The project's build stripped the binaries, so there are no debug symbols to split | Remove `-s` from its link or install flags |
| `ldflags` (`didn't pass LDFLAGS`, no `GNU_HASH`) | The link didn't use `${LDFLAGS}` | Pass `${LDFLAGS}` |
| `file-rdeps` | A file needs something no `RDEPENDS` provides, often `/bin/bash` or `python3` for a script | `RDEPENDS:${PN} += "bash"` |
| `buildpaths` | A build machine path is in an installed file | Fix the project's build; it breaks reproducibility |
| `arch` | A binary for the wrong architecture, usually a prebuilt one | Rebuild it, or `INSANE_SKIP:${PN} += "arch"` if it's intended |
| `dev-so` | An unversioned `.so` in the main package | Normal for plugins: `INSANE_SKIP:${PN} += "dev-so"`, or `FILES_SOLIBSDEV = ""` |

`INSANE_SKIP` silences a check for one package. Use it when you understand why the check doesn't apply, not to make an error go away.

## 20. Reproducible builds, licenses, vulnerabilities and updates

**Pin everything.** A product build must give the same image in two years:

- **Layers at fixed commits.** Record each layer's repository and revision in a file in version control. `bitbake-setup` reads such a file (a configuration in JSON); `bitbake-layers create-layers-setup <dir>` writes one from the current checkout with a script to restore it. Many teams use `kas` or `repo` for the same purpose.
- **Recipes at fixed revisions.** `SRCREV = "${AUTOREV}"` builds whatever the branch holds today: fine during development, never in a release.
- **Source archived.** Upstream servers disappear. Keep `DL_DIR`, and serve it as a mirror:

```
BB_GENERATE_MIRROR_TARBALLS = "1"                    # also keep git clones as tarballs
INHERIT += "own-mirrors"
SOURCE_MIRROR_URL = "https://mirror.example.com/yocto-sources"
BB_NO_NETWORK = "1"                                  # release builds: fail instead of downloading
```

- **The build machine in a container.** The host distribution is the one input the layers don't pin.

OE-Core's builds are bit-for-bit reproducible, and tested for it. Your own recipes are too when they avoid timestamps and build paths; the `buildpaths` check catches the second.

**Licenses.** Every recipe declares its license, so the build can report and enforce them:

| Need | How |
|---|---|
| The list of licenses in the image | `tmp/deploy/licenses/<machine>/<image>/license.manifest` |
| The license texts on the board | `COPY_LIC_MANIFEST = "1"`, `COPY_LIC_DIRS = "1"` |
| The source of everything shipped, for GPL compliance | `INHERIT += "archiver"`, `ARCHIVER_MODE[src] = "original"` |
| No GPLv3 in the image | `INCOMPATIBLE_LICENSE = "GPL-3.0* LGPL-3.0* AGPL-3.0*"`; the build fails if a package needs one |
| Software with license restrictions (some codecs, firmware) | Refused until accepted: `LICENSE_FLAGS_ACCEPTED = "commercial"` |

Release 6.1 requires `LICENSE` to be an SPDX expression (`MIT AND BSD-3-Clause`, not `MIT & BSD-3-Clause`).

**SBOM.** Each image build writes a software bill of materials in SPDX 3 format (`<image>.spdx.json` next to the image): every package, its version, license, source and patches. It's the input for vulnerability scanners and what customers and regulations (the EU Cyber Resilience Act) ask for.

**Vulnerabilities.** Since 6.0, the check runs on the SBOM:

```sh
$ bitbake-config-build enable-fragment core/yocto/sbom-cve-check
$ bitbake bbb-image
```

It writes `.sbom-cve-check.yocto.json` and `.sbom-cve-check.spdx.json` reports next to the image, listing each known CVE as patched, unpatched or ignored. Mark a CVE that doesn't apply with `CVE_STATUS[CVE-2026-12345] = "not-applicable-config: feature not built"`. The `cve-check` class of earlier releases (`INHERIT += "cve-check"`) was removed. Fixes come from the release's point releases (6.0.1, 6.0.2...): updating the layers to the latest one is the regular security maintenance of a product.

**Hardening the image.** The development settings must not ship:

| Development | Product |
|---|---|
| `core/yocto/root-login-with-empty-password`, `allow-empty-password`, `empty-root-password` | Removed. A root password hash, or no password logins at all |
| `tools-debug`, `dbg-pkgs`, `package-management` | Removed |
| Writable root | `IMAGE_FEATURES += "read-only-rootfs"`, data on its own partition |
| SSH with passwords | Keys only |

Setting a root password hash, in the image recipe (`\$` keeps BitBake and the shell from expanding the `$` of the hash):

```
inherit extrausers
EXTRA_USERS_PARAMS = "usermod -p '\$6\$<salt>\$<hash>' root;"
```

Generate the hash with `openssl passwd -6` (rootfs note, section 8). Poky already builds with the compiler's hardening flags (`security_flags.inc`).

**Updates.** Yocto builds the images; an update framework installs them in the field, each with its own layer:

| Framework | Layer | Model |
|---|---|---|
| SWUpdate | `meta-swupdate` | A/B or rescue system, flexible handlers |
| RAUC | `meta-rauc` | A/B slots, signed bundles |
| Mender | `meta-mender` | A/B with a management server |
| OSTree | `meta-updater` and others | File-level, atomic deployments |

The rootfs note (section 16) covers the A/B principle and the bootloader's part in it.

**Size.** `core-image-minimal` with glibc and SysV init is **typically** under 10 MiB without kernel modules. To go lower: `TCLIBC = "musl"`, `INIT_MANAGER = "mdev-busybox"`, fewer `DISTRO_FEATURES`, only the needed `kernel-module-*` packages instead of `kernel-modules`, and `IMAGE_LINGUAS = ""`. The `poky-tiny` distro shows these together. Build history (section 19) shows which package the space goes to.

## 21. Releases and upgrades

A release comes every six months, in April and October. Every two years, the April release is an LTS, supported for four years; the others are supported for seven months.

| Release | Codename | Date | Support |
|---|---|---|---|
| 5.0 | Scarthgap | April 2024 | LTS, until April 2028 |
| 5.1, 5.2, 5.3 | Styhead, Walnascar, Whinlatter | October 2024, April 2025, late 2025 | Ended, or ending soon |
| 6.0 | Wrynose | April 2026 | LTS, until April 2030 |
| 6.1 | Blacksail | October 2026 | Until April 2027 |

**Start a product on the current LTS**, and take its point releases. Every layer must be on the branch of the same release: mixing a `scarthgap` BSP layer with `wrynose` OE-Core is the classic source of parse errors, and `LAYERSERIES_COMPAT` exists to refuse it. The BSP layer usually decides: check which releases the vendor supports before choosing.

**Why old tutorials fail.** The changes between 5.0 and 6.1 that break recipes and instructions written before them:

| Since | Change | What to do |
|---|---|---|
| 5.1 | Source is unpacked in `UNPACKDIR`, not `WORKDIR`. `S = "${WORKDIR}"` is an error | `S = "${UNPACKDIR}"`; `${UNPACKDIR}/file` in `do_install` |
| 5.2 | `debug-tweaks` removed | The four image features of section 10, or the fragment |
| 5.2 | `branch=` mandatory in `git://` URLs | Add it |
| 5.2 | `virtual/${TARGET_PREFIX}gcc` renamed | `virtual/cross-cc`, `virtual/cross-c++`, `virtual/cross-binutils` |
| 5.3 | The `poky` repository's `master` is frozen | `bitbake-setup`, or the three repositories (section 4) |
| 5.3 | `S = "${WORKDIR}/git"` | Remove the line |
| 5.3 | `KERNEL_IMAGETYPE = "fitImage"` and `kernel-fitimage` removed | The `kernel-fit-image` class and `linux-yocto-fitimage` recipe |
| 6.0 | `cve-check` removed | `core/yocto/sbom-cve-check` |
| 6.0 | `systemd` and `sysvinit` can't be combined; five distro features added by default | `INIT_MANAGER`; `DISTRO_FEATURES_OPTED_OUT` |
| 6.0 | `pkg-config` variables no longer set for every recipe | `inherit pkgconfig` |
| 6.0 | `.wks` files must be in `files/wic/` | Move them |
| 6.0 | SPDX 2.2 removed | SPDX 3 only |
| 6.1 | `LICENSE` must be an SPDX expression | `AND`, `OR`, `WITH`; `scripts/contrib/convert-spdx-licenses.py` converts |
| 6.1 | `GROUPMEMS_PARAM` replaced | `USERMOD_PARAM` |

**Upgrading a product** from one LTS to the next: read every migration guide in between, move all layers to the new branch together, set `LAYERSERIES_COMPAT` in your layer, then fix the parse errors, the build errors and the QA errors in that order. `devtool upgrade` helps with your own recipes' versions.

**Other boards.** For a Raspberry Pi 4 in 64-bit mode, the steps are the same with the vendor layer:

```sh
$ git clone -b wrynose https://git.yoctoproject.org/meta-raspberrypi ../layers/meta-raspberrypi
$ bitbake-layers add-layer ../layers/meta-raspberrypi
$ bitbake-config-build enable-fragment machine/raspberrypi4-64
```

`ENABLE_UART = "1"` in the configuration turns the serial console on. The image, the distro and the `hello` recipe don't change: that's the point of separating the machine from the rest.

## 22. Troubleshooting by symptom

**Setup and parsing:**

| Symptom | Likely cause | Check, then see |
|---|---|---|
| `bitbake: command not found` | The environment script wasn't sourced in this shell | `source $SETUP/build/init-build-env` (section 5) |
| `Do not use Bitbake as root.` | Building as root, often in a container | Run as a normal user (section 3) |
| `Your system needs to support the en_US.UTF-8 locale.` | Locale not generated | `sudo dpkg-reconfigure locales` (section 3) |
| `Layer <x> is not compatible with the core layer which only supports these series: wrynose` | The layer is on another release's branch | Check out its `wrynose` branch (section 21) |
| `Layer '<x>' depends on layer '<y>', but this layer is not enabled` | A dependency isn't in `bblayers.conf` | `bitbake-layers add-layer` for it first (section 7) |
| `No recipes in default available for: ...bbappend` | The appended recipe doesn't exist: missing layer or changed version | `%` in the file name; add the layer (section 12) |
| `Nothing PROVIDES '<x>'` | No recipe of that name: typo, missing layer, or a package name used where a recipe name is needed | `bitbake-layers show-recipes`; the Layer Index (section 7) |
| `<x> was skipped: incompatible with machine <m>` | `COMPATIBLE_MACHINE` doesn't list the machine | Set it in an append file if the recipe really works there (section 13) |
| `ParseError ... unparsed line`, on `VAR_append` | Old override syntax | `VAR:append` (section 15) |
| `MACHINE=<x> is invalid` | No such machine file in the enabled layers | `ls` the layers' `conf/machine/` (section 9) |
| My recipe isn't found | Wrong directory depth for `BBFILES` | `recipes-*/<name>/<name>_<ver>.bb` (section 7) |

**Fetching:**

| Symptom | Likely cause | Check, then see |
|---|---|---|
| `Fetcher failure for URL ... Unable to fetch` | Network, proxy, or the upstream file is gone | Try the URL by hand; a source mirror (section 20) |
| `Checksum mismatch!` | The upstream file changed, or a proxy returned an error page | Look at the file in `DL_DIR`; update `SRC_URI[sha256sum]` only if the change is legitimate |
| `Unable to find revision <hash> in branch <b>` | `SRCREV` isn't on the branch named in `SRC_URI` | Fix `branch=` (section 8) |
| `The URL ... does not set any branch parameter` | Old recipe | Add `;branch=` (section 21) |
| `Network access disabled through BB_NO_NETWORK` | A source isn't in `DL_DIR` or the mirror | `bitbake --runall=fetch <image>` with the network on (section 20) |

**Building:**

| Symptom | Likely cause | Check, then see |
|---|---|---|
| `do_compile` fails with `fatal error: foo.h: No such file or directory` | The library isn't in `DEPENDS` | Add it; look in `recipe-sysroot/usr/include` (sections 6, 8) |
| `configure` doesn't find a library that is in `DEPENDS` | `pkg-config` not available to the recipe | `inherit pkgconfig` (section 8) |
| `S = "${WORKDIR}"` or `${WORKDIR}/git` reported as an error | Recipe written before 5.1 or 5.3 | Section 21 |
| `do_install` can't find a `file://` file in `${WORKDIR}` | It's in `UNPACKDIR` since 5.1 | `${UNPACKDIR}/<file>` (section 8) |
| `LIC_FILES_CHKSUM` mismatch | The license file changed in a new version | Read the change, then update the checksum (section 8) |
| `c++: fatal error: Killed signal terminated program cc1plus` | Out of memory | Lower `BB_NUMBER_THREADS` and `PARALLEL_MAKE = "-j 4"` in `local.conf`; add swap (section 3) |
| `No space left on device` | `tmp/` filled the disk | `INHERIT += "rm_work"` deletes each work directory after its recipe is built (section 6) |
| A QA error stops `do_package_qa` | See the table of section 19 | Section 19 |
| The build stops at once with `pseudo` abort messages | Files in the work directory changed outside the build | `bitbake -c clean <recipe>`, and don't edit under `tmp/work` |
| A build works on one machine and not another | Host tool leaking in, or different layer revisions | Compare the build configuration headers (section 5) |

**Changes that have no effect:**

| Symptom | Likely cause | Check, then see |
|---|---|---|
| A variable set in `local.conf` isn't applied | A recipe or a later line overrides it; `+=` instead of `:append` | `bitbake-getvar -r <recipe> VAR` (sections 15, 19) |
| An append file isn't applied | The layer isn't enabled, the name doesn't match, or the directory depth is wrong | `bitbake-layers show-appends` (section 19) |
| A `file://` in my layer isn't the one used | `FILESEXTRAPATHS` missing, or `=` instead of `:=` | Section 12 |
| A kernel option from my fragment isn't in the kernel | Unmet dependencies, or the fragment isn't in `SRC_URI` | `bitbake -c kernel_configcheck -f virtual/kernel` (section 13) |
| Edits to a recipe in my layer are ignored | The recipe is still in the `devtool` workspace | `devtool status`, `devtool reset` (section 16) |
| A package is built but isn't in the image | Not in `IMAGE_INSTALL`, or the recipe name was used where the package has another name | The image's `.manifest`; `oe-pkgdata-util` (section 19) |
| Everything rebuilds after a small change | The change touched the distro, the toolchain or a widely used library | `bitbake -S printdiff` (section 18) |

**On the board:**

| Symptom | Likely cause | Check, then see |
|---|---|---|
| Nothing on the serial console | The card doesn't hold the `.wic`, or the board booted from eMMC | Write the `.wic`, not the `.ext4`; hold S2 (section 9) |
| The kernel boots, no login prompt | `SERIAL_CONSOLES` doesn't name the real console | `ttyS0` (section 9; rootfs note, section 7) |
| `root` can't log in | No empty-password feature and no password set | Section 20 for a product; the fragment for development (section 5) |
| `VFS: Unable to mount root fs` | The `.wks` and the kernel command line disagree, or a driver is missing | `wic ls`; kernel note, section 13 |
| A program fails with `not found` or missing libraries | Copied by hand from another toolchain | Build it with a recipe or the SDK (sections 8, 17) |
| `modprobe` finds no modules | `kernel-modules` not in the image, or a kernel from another build | `IMAGE_INSTALL`; `uname -r` and `/lib/modules` (section 13) |
| A program built with the SDK fails on the board with `GLIBC_2.xx not found` | The SDK is newer than the image on the board | Rebuild both from the same revision (section 17) |
